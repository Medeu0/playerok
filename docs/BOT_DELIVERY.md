# Доставка knowledge-product ботом (single-file HTML)

Этот документ описывает, как **существующий** Playerok-бот (он не находится
в этом репозитории) должен доставлять купленный knowledge-product. Здесь не
описывается конкретный Playerok API — только контракт со стороны Guide
Engine: что собирается, где лежит и как называется.

## Что производит этот репозиторий

```bash
npm run build:file -- --product=army-ss
```

даёт один файл:

```text
dist/army-ss.html
```

— полностью самодостаточный HTML (CSS и JS встроены, датасет встроен,
никаких обращений к серверу для работы). Рядом кладётся необязательный
`dist/army-ss.build.json` со служебными метаданными сборки (версия,
verifiedAt, размер, время сборки) — он не отправляется покупателю, это
справочная информация для бота/оператора.

## Flow

```text
paid order (Playerok)
    → бот определяет SKU по офферу/названию товара
    → бот берёт готовый dist/<sku>.html из своего хранилища сборок
    → бот отправляет файл покупателю в чат Playerok
```

Никакой сетевой выдачи прав, токенов или редиректов не требуется — весь
продукт уже находится внутри файла, который получает покупатель.

## Пример сопоставления SKU → файл

```js
const skuToFile = {
  'army-ss': '/path/to/dist/army-ss.html',
  // будущие SKU добавляются сюда по мере готовности:
  // 'police-ss': '/path/to/dist/police-ss.html',
};

function resolveFile(sku) {
  const file = skuToFile[sku];
  if (!file) throw new Error(`No built file for SKU "${sku}"`);
  return file;
}
```

Как именно бот определяет `sku` из данных заказа (по названию оффера, по
внутреннему id и т.п.) — решение самого бота; здесь только соглашение об
именах файлов (`<sku>.html`, тот же `sku`, что и `content/<sku>/`).

## Когда нужно пересобрать файл

Пересоберите `dist/<sku>.html` (и обновите то, что раздаёт бот) после любого
изменения контента (`content/<sku>/*.json`), например при обновлении версии
правил или добавлении вопросов в quiz. Файл, который бот отправляет —
статический снимок на момент сборки; автоматической синхронизации с
`content/` в рантайме нет (в этом и была цель — ноль бэкенда).

## Что сюда специально не входит

- Нет access API, подписанных ссылок, revoke — это отдельное, более сложное
  направление, которое сейчас сознательно отложено (см. историю задач).
- Нет per-buyer персонализации/водяных знаков — все покупатели получают
  идентичный файл для данного SKU. Если позже понадобится ограничивать
  распространение — это отдельный этап поверх текущей архитектуры, не
  блокирующий её.
- Нет предположений о конкретном Playerok API вызова отправки файла — это
  зона ответственности существующего бота.
